# 01: 运维账号凭据采用非明文存储，移除启动配置中的明文密码

Category: bug
Status: needs-triage

## 原始需求

运维账号要存密文而非明文。

## 现状核对

运维账号写入数据库的密码已经经过 bcrypt 哈希，并非明文。当前需要处理的是启动配置：`Operator.Password` 接收明文密码，启动时用于创建运维账号，或在与数据库密码不一致时重置密码。

因此本票聚焦运维启动凭据的非明文存储，不将问题误记为“数据库保存明文密码”。对于用于登录校验的密码，“密文”应进一步区分为不可逆密码哈希与可逆加密；具体方案在分诊时确定。

## 代码依据

- `config.yaml.sample`、`internal/conf/config.yaml`：示例配置提供 `Operator.Password` 字段，默认值为空。
- `internal/conf/setting.go`：`OperatorConf.Password` 为启动配置中的密码输入。
- `cmd/serve/serve.go`：`ensureOperatorAccount` 创建时调用 `utils.HashPassword(op.Password)`；已有账户使用明文配置值比对，不一致则重新哈希并重置密码。
- `pkg/utils/password.go`：密码存储和校验使用 bcrypt。

本次没有读取本地真实密码配置，也没有发现或记录任何实际凭据值。

## 预期结果

- 运维账号的启动流程不再要求将明文登录密码持久保存在普通配置文件中。
- 数据库继续保存用于密码校验的安全哈希，不保存明文或可直接用于登录的凭据。
- 启动、日志、错误响应和配置展示不泄露明文密码或密码哈希。
- 明确运维账号首次创建、密码更新及重启后的行为，避免旧配置意外覆盖已修改的密码。
- 配置示例、部署说明与最终方案一致。

## 待明确

- 启动配置是否直接接收预先生成的密码哈希，或改用独立凭据初始化流程、受控秘密来源。
- 若采用可逆加密，解密密钥如何独立保存；不得将密文和解密密钥放在同一普通配置中。
- 是否继续保留“配置为准，启动时重置运维密码”的行为。
- 新方案的配置字段、初始化工具、错误处理及验证方式。
